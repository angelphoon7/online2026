C1  IntentCommitted carries every Intent field                        ** PASS **
    All 12 struct fields are present with matching types. `intentHash` is the indexed key;
    `owner` and `eventId` are indexed topics (still decodable by graph-node). No field is
    missing, so the subgraph can reconstruct the full signed intent from the event alone.
    No contract change needed.

C2  Which hash does the registry key on                               ** PASS **
    src/IntentRegistry.sol:114-126 -- the key is the BARE STRUCT HASH (`structHash =
    hashIntent(i)`), NOT the EIP-712 digest. The digest
    (keccak256("\x19\x01" ++ DOMAIN_SEPARATOR ++ structHash), line 115) is used only for
    ecrecover. `state[]`, `intentOwner[]` and the emitted `intentHash` all use structHash.

    solver/src/hash.ts computes exactly this: same typehash string, same field order, and
    hashOffered = keccak256(abi.encodePacked(offered)). Verified empirically -- recomputing
    all three seed intents from deployments/arc-testnet.json reproduces the committed hashes:
      0xc949a634...6e8ed8  MATCH
      0x3dd1dad0...2dafe8  MATCH
      0xf1379158...686835  MATCH
      INTENT_TYPEHASH = 0x91f516d8c49db0dc6f0c19637e160da3ebab539eb1d439344398a2c1e8a14488
    This is the hash-binding implementation for plan rule 1; it is the one to lift into
    shared/intent.ts in step 5-A.

    CAVEAT (not a failure, but a step-5 blocker if missed): lib/contracts.ts:212 `hashIntent`
    is NOT a local implementation -- it is an eth_call to IntentRegistry.hashIntent. It cannot
    be used for snapshot hash binding (one RPC per intent, and it defeats the point of
    checking the indexer independently). shared/intent.ts must export the pure TS version from
    solver/src/hash.ts, and the frontend should switch to it.

C3  Is there an event telling the subgraph which intents settled       ** PASS (case A) **
    Settlement emits `Settled(address indexed proposer, bytes32[] intentHashes,
    uint256 participantCount)`. The intent hashes are in the event, so handleSettled can flip
    each listed Intent to SETTLED. No D2 fallback, no RPC state sweep, no contract change.
    IntentRegistry.markSettled() is silent (no event) -- that is fine; Settled covers it.

    LIMITATION for schema 3-D: `Settled` carries NO per-leg data (no receives[], no
    netPayment[], no participants[]). The `SettlementLeg` entity in the plan CANNOT be built
    from events as the contract stands. Options, in order of preference:
      (a) drop SettlementLeg; keep Settlement{proposer, txHash, block, timestamp,
          participantCount, intents[]} and leave per-leg display on the existing RPC path.
      (b) if a redeploy happens for another reason, widen Settled to carry legs.
    Do NOT redeploy solely for this -- it is on the plan's own cut list.

C4  Does settle() need signatures                                     ** PASS **
    settle(Intent[], Leg[]) -- no `bytes[] sigs`. Signatures are verified once in commit();
    V0 re-binds the supplied struct to the live hash. Therefore the subgraph does NOT need to
    store `signature`, and the `signature: Bytes!` field mentioned in plan 3-D is not needed.

C5  Is ticket metadata reachable                                      ** PASS (both ways) **
    (i) `TicketMinted` already carries eventId, sessionId, sectionId, row, seat.
    (ii) `meta(uint256)` is a public getter returning only value types
         (uint32, uint16, uint16, uint16, uint16, uint8) -- safe for eth_call from a handler.
    Prefer (i): add handleTicketMinted and read the event fields directly. No eth_call in the
    mint path, so the plan's helpers.ts try_meta() fallback becomes belt-and-braces only.
    Redemption status: `TicketRedeemedEvt(uint256 indexed tokenId, address indexed holder)`
    -- NOTE THE NAME. The plan (3-E, 3-F) writes `TicketRedeemed`; that is the name of a
    Settlement *error*, not the event. The subgraph.yaml entry must be
      TicketRedeemedEvt(indexed uint256,indexed address)
    and the handler must take a `TicketRedeemedEvt` event type.

Corrections the plan must absorb before step 3:
  1. All `contracts/` paths -> repo root.
  2. Event name is TicketRedeemedEvt, not TicketRedeemed.
  3. Settled signature is (indexed address, bytes32[], uint256) -- three params.
  4. Drop `signature: Bytes!` from the Intent entity (C4).
  5. Drop SettlementLeg, or accept it cannot be populated from events (C3).
  6. Index TicketMinted for metadata instead of eth_call'ing meta() on first sight (C5).
  7. Escrow emits TicketEscrowed/TicketWithdrawn carrying the depositor -- these are more
     direct than deriving custody from Transfer. Recommend indexing Escrow as a dataSource
     for `depositor`, and keeping Transfer for `owner`. The plan's Transfer-only derivation
     also works (Escrow.deposit does transferFrom into the Escrow, confirmed at
     Escrow.sol:41); using both gives a free cross-check.
  8. Escrow does NOT implement IERC721Receiver, so a direct safeTransferFrom to it reverts.
     Custody can therefore only begin via deposit(), which always sets depositor[] and emits.
  9. Step 1-A's export-deployment.ts does not apply; deployments/arc-testnet.json already
     exists in a different shape (C6).
